# Работа с Codex

Настройки хранятся в репозитории и используют существующие требования,
архитектуру и команды проекта.

Модель и глубина рассуждения наследуются из выбранных пользователем настроек.
Проектная конфигурация загружается для доверенного репозитория. После изменения
инструкций или добавления навыков начните новую задачу Codex, чтобы проверить их
обнаружение. Можно попросить: «Перечисли инструкции и проектные навыки,
которые доступны в этой задаче».

Автоматически создаваемый блок Next.js в `AGENTS.md` сохраняется. Перед изменением
Next.js-кода агент читает нужный раздел документации установленной версии в
`node_modules/next/dist/docs/`.

## Подготовка checkout и worktree

Активируйте Node.js 24 через используемый менеджер версий и pnpm, указанный в
`package.json#packageManager`. Проверьте `node --version` и `pnpm --version`.
Для `.nvmrc` можно использовать `nvm use`, если установлен nvm.
Node.js 24 должен быть доступен и в терминале, который запускает действия Codex:
скрипт проверяет runtime, но не устанавливает его и не меняет глобальную версию.

```bash
pnpm setup:codex
```

[Скрипт подготовки](../scripts/codex-setup.mjs) проверяет версии, выполняет
`pnpm install --frozen-lockfile` и `pnpm db:generate`. Codex запускает этот же скрипт
при подготовке нового worktree.

Для генерации Prisma Client скрипт передаёт дочернему процессу технический
`DATABASE_URL` с локальным адресом. Генерация не требует соединения с PostgreSQL.
Файлы `.env` остаются под контролем разработчика: скрипт не переносит секреты
между checkout и не применяет миграции.

Для запуска приложения настройте отдельную локальную базу и `.env.local` по
[README](../README.md#локальный-запуск). У разных worktree могут быть несовместимые
миграции; для таких задач используйте отдельные базы. Если основной checkout уже
запущен, другой экземпляр можно стартовать командой `pnpm dev --port 3001`.

Действия окружения:

- **Run** — `pnpm dev`;
- **Check** — `pnpm check`;
- **Build** — `pnpm build`.

## Проверки и ревью

Перед передачей изменений кода или исполняемой конфигурации выполните:

```bash
pnpm check
pnpm build
```

`check` последовательно запускает Prettier, ESLint, TypeScript и Vitest.
`typecheck` сначала выполняет `next typegen`, чтобы типы маршрутов были доступны
в чистом worktree до первого запуска сервера или сборки. Prettier
также проверяет проектный `SKILL.md`. Для правок только документации достаточно
проверить форматирование изменённых файлов и ссылки. Для форматирования отдельных
файлов используйте `pnpm exec prettier --write <файлы>`; общий `pnpm format`
изменяет весь репозиторий, включая чужую незавершённую работу.

`pnpm build` читает конфигурацию Prisma и Next.js. Для сборки без базы можно
передать технический адрес только этой команде:

```bash
DATABASE_URL=postgresql://codex:codex@127.0.0.1:1/weekly_system_codegen pnpm build
```

Успешная сборка не подтверждает миграции, login или доступ к данным. Проверки,
которым нужна база, выполняются отдельно на предназначенной для разработки базе.
E2E-команда пока не реализована; для изменений UI проверяется соответствующий
сценарий в браузере на мобильной и широкой ширине.

Для независимого ревью можно попросить: «Поручи `weekly_reviewer` проверить
изменения в этой задаче». Агент ищет воспроизводимые дефекты и возвращает
замечания с файлами, строками и условиями возникновения. Его профиль задаёт режим
только для чтения; фактические разрешения также зависят от текущей сессии Codex.

Для изменений данных можно явно вызвать `$weekly-data-change`. Навык также
доступен для автоматического выбора по описанию задачи. Он помогает проверить
владельца записей, локальные даты, идемпотентность и совместимость миграций.
