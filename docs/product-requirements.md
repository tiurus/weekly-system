# Weekly System — требования к веб-приложению

Статус: draft  
Версия: MVP  
Дата: 2 сентября 2026

## 1. Назначение

Weekly System — персональное веб-приложение, которое помогает определить достаточную нагрузку на сегодня с учётом энергии, сна и внешнего напряжения.

Приложение заменяет перегруженную недельную матрицу привычек коротким циклом:

1. оценить состояние;
2. получить подходящий режим дня;
3. выполнить не более трёх обязательных действий;
4. отдельно учитывать недельные активности;
5. сделать короткий недельный обзор.

Главная продуктовая метрика — доля дней с выполненным реалистичным минимумом среди дней, когда пользователь сделал запись.

## 2. Проблема текущего решения

Текущий Notion-дашборд требует до 119 отметок привычек и около 28 полей check-in за неделю. Он смешивает ежедневные действия, редкие активности, диагностику и нежелательные события в одной модели. Собранное состояние не меняет рекомендуемую нагрузку, а история и графики конкурируют с действиями на сегодня.

Веб-версия должна устранить эти ограничения на уровне пользовательского сценария и модели данных, а не воспроизводить интерфейс Notion.

### Подтверждённые ограничения первой итерации

- В ближайшее время приложением пользуется один владелец.
- Модель данных сохраняет владельца сущностей, чтобы позднее добавить других пользователей без переделки домена.
- В MVP есть один заранее настроенный пользователь и простой вход по логину и паролю.
- Самостоятельной регистрации, восстановления пароля, ролей и админ-панели нет.
- Сайт разворачивается на собственном сервере, а не на Vercel.
- Production URL: `https://habbit.merdev.site`.
- Nginx Proxy Manager на `https://nginx.merdev.site` завершает TLS и направляет трафик к приложению.
- Порт приложения и база данных не публикуются напрямую в интернет.
- Из Notion вручную переносятся только актуальные настройки, опоры и недельные цели. История остаётся архивом в Notion.

## 3. Цели MVP

- Завершать утренний check-in за 30 секунд или быстрее.
- Показывать не более трёх обязательных действий на день.
- Автоматически определять текущий день и неделю в часовом поясе пользователя.
- Предлагать режим `Минимум`, `Обычный` или `Ресурс` на основе check-in.
- Позволять изменить предложенный режим одним действием.
- Учитывать недельные активности количеством сессий, а не семью дневными чекбоксами.
- Отделять отсутствие данных от невыполнения.
- Работать на телефоне и ноутбуке без горизонтального скролла.

## 4. Границы MVP

### Входит

- Один внутренний профиль владельца, вход по логину и паролю и приватные данные.
- Экран `Сегодня`.
- Утренний check-in.
- Три режима нагрузки.
- Три ежедневные опоры.
- До трёх недельных целей.
- Учёт завершённых сессий.
- Короткий вечерний итог.
- Недельный обзор и история последних недель.
- Настройка часового пояса и базовых действий.
- Self-hosted deployment за Nginx Proxy Manager.

### Не входит

- Социальные функции и публичные профили.
- Совместные пространства и команды.
- Регистрация, восстановление пароля, роли и управление пользователями.
- Сложная геймификация, XP, уровни и награды.
- Обнуляемые streak-серии.
- Push-уведомления.
- Полная миграция истории из Notion.
- Медицинские рекомендации на основании HRV, сна или энергии.

## 5. Пользовательский сценарий

### Вход

1. Неавторизованный пользователь открывает приложение.
2. Приложение перенаправляет его на `/login`.
3. Пользователь вводит единственный настроенный логин и пароль.
4. После успешной проверки приложение создаёт серверную сессию и возвращает пользователя на исходный защищённый маршрут.
5. Ошибка входа не сообщает, что именно неверно: логин или пароль.

### Утро

1. Пользователь открывает `/today`.
2. Приложение показывает локальную дату и текущую неделю.
3. Пользователь выбирает энергию и качество сна по шкале 1–3.
4. При желании выбирает фон и добавляет короткую заметку.
5. Приложение рассчитывает предложенный режим.
6. Пользователь принимает его или меняет одним нажатием.
7. На экране отображаются три действия соответствующего размера.

### В течение дня

- Действие отмечается одним нажатием с мгновенным визуальным подтверждением.
- Выполненная недельная активность добавляется кнопкой `+1 сессия`.
- Ошибочное действие можно отменить без перезагрузки страницы.
- Приложение сохраняет изменения автоматически.

### Вечер

- Пользователь видит, выполнен ли минимум дня.
- Может оставить одну короткую заметку о главном факторе дня.
- Незавершённые действия не требуют обязательного объяснения.

### Конец недели

1. Пользователь открывает `/week/review`.
2. Видит дни с записью, выполнение дневного минимума и прогресс недельных целей.
3. Отвечает на вопросы `Что поддерживало?` и `Что изменить?`.
4. Задаёт один главный результат следующей недели.
5. Выбирает до трёх недельных целей и не более одного ограничения.

## 6. Информационная архитектура

### `/today` — основной экран

Порядок блоков:

1. локальная дата и главный результат недели;
2. check-in состояния;
3. выбранный режим и короткое объяснение;
4. три опоры дня;
5. до трёх недельных целей с прогрессом;
6. вечерняя заметка;
7. ссылка на недельный обзор.

Графики и полная история не размещаются выше ежедневных действий.

### `/week`

- Диапазон текущей недели.
- Главный результат недели.
- Семь компактных статусов дней: `нет записи`, `минимум выполнен`, `частично`.
- Прогресс недельных целей в формате `факт / цель`.
- Одно активное ограничение недели.

### `/week/review`

- Итоги текущей недели.
- Два текстовых вопроса для рефлексии.
- Настройка следующей недели.
- Явное действие `Завершить неделю`.

### `/history`

- Последние четыре недели по умолчанию.
- Пагинация или дозагрузка более ранних периодов.
- Средние значения энергии и сна.
- Выполнение минимума только среди дней с check-in.
- Без сравнения пользователя с другими людьми.

### `/settings`

- Часовой пояс.
- Начало недели: для MVP — понедельник.
- Тексты трёх ежедневных опор и их варианты по режимам.
- Каталог недельных активностей.
- Экспорт и удаление данных.

Удаление данных должно требовать отдельного подтверждения с явным описанием последствий.

### `/login`

- Поля `Логин` и `Пароль`.
- Кнопка `Войти`.
- Общая ошибка `Неверный логин или пароль`.
- Возможность показать или скрыть пароль локально в поле.
- После успешного входа — возврат на ранее запрошенный внутренний маршрут.
- Страница недоступна в авторизованной сессии: пользователь перенаправляется на `/today`.

## 7. Режимы нагрузки

Режимы — это три варианта одного контракта `Фокус → Тело → Закрытие`. Набор опор не меняется, меняется требуемая глубина. Ресурсный режим не добавляет обязательные чекбоксы и не наказывает пользователя дополнительной нагрузкой за хорошее состояние.

| Опора     | 🔴 Минимум                                       | 🟡 Обычный                                                            | 🟢 Ресурс                                                |
| --------- | ------------------------------------------------ | --------------------------------------------------------------------- | -------------------------------------------------------- |
| Фокус     | 20 минут на главной задаче                       | один фокус-блок 60–90 минут                                           | сложная задача или два блока по 60 минут                 |
| Тело      | выйти из дома и пройтись 15 минут                | 30–45 минут движения или тренировка                                   | полноценная тренировка или интенсивная активность        |
| Закрытие  | прекратить рабочие дела к установленному времени | закрыть работу, выполнить вечерний ритуал и не возвращаться к задачам | закрыть работу и за 5 минут определить главное на завтра |
| Успех дня | выполнены все три опоры                          | выполнены все три опоры                                               | выполнены все три опоры                                  |

### Минимум

Назначение — сохранить ритм в тяжёлый день, а не поставить рекорд. Выполнение трёх минимальных опор отображается как 100% плана текущего режима, а не как частичное выполнение обычного плана.

### Обычный

Дефолтный повторяемый день, а не идеальный максимум. Лыжи, настольный теннис, встречи и другие нерегулярные активности остаются на недельном уровне и не появляются как ежедневные требования.

### Ресурс

Использует хорошее состояние для качества и продвижения. Меняется глубина тех же трёх опор, но не их количество.

### Расчёт режима

```text
если energy = 1 или sleep = 1 → MINIMUM
иначе если energy = 3 и sleep >= 2 → RESOURCE
иначе → NORMAL
```

Ручной выбор пользователя имеет приоритет до конца локального дня. Интерфейс должен различать `предложенный` и `выбранный` режимы. HRV, сон и субъективная энергия являются сигналами, а не абсолютной истиной; приложение рекомендует режим, но не блокирует другой выбор.

Алгоритм является организационной подсказкой, а не медицинской интерпретацией состояния.

## 8. Типы отслеживаемого поведения

| Тип                       | Способ учёта                               | Пример                  |
| ------------------------- | ------------------------------------------ | ----------------------- |
| Диагностика               | значение без очков                         | энергия, сон, HRV       |
| Ежедневная опора          | один статус за текущий день                | закрыть рабочий день    |
| Недельная активность      | количество сессий                          | кардио, лыжи, встреча   |
| Инструмент восстановления | рекомендация по режиму                     | дневной сон, медитация  |
| Ограничение               | одно выбранное правило или журнал эпизодов | соцсети во время фокуса |

### Правила формулировок

- Название ежедневного действия должно описывать наблюдаемое завершение.
- Составные формулировки вроде `медитация или чтение` заменяются общей целью с необязательным указанием типа активности.
- `Выполнение тасок` заменяется конкретным главным результатом дня.
- Нежелательное поведение должно иметь явную семантику: `день без X` либо `произошёл эпизод X`.
- В один момент активно не более одного ограничения.

## 9. Функциональные требования

- **FR-001. Текущая дата.** Сервер и клиент определяют день в сохранённом часовом поясе пользователя, а не только по UTC устройства.
- **FR-002. Текущая неделя.** Неделя автоматически рассчитывается от понедельника до воскресенья.
- **FR-003. Уникальный дневной лог.** Для пользователя и локальной даты существует не более одной записи.
- **FR-004. Check-in.** Энергия и сон обязательны для расчёта режима; остальные поля необязательны.
- **FR-005. Автовыбор режима.** После ввода обязательных значений режим рассчитывается без отдельной отправки формы.
- **FR-006. Ручной режим.** Пользователь может изменить режим одним действием; выбор сохраняется.
- **FR-007. Три опоры.** Основной экран показывает ровно три обязательных действия после check-in.
- **FR-008. Адаптивные формулировки.** Размер и текст действий зависят от итогового режима.
- **FR-009. Автосохранение.** Изменения сохраняются автоматически с состояниями `сохраняется`, `сохранено`, `ошибка`.
- **FR-010. Повтор операции.** Повторный сетевой запрос не создаёт дубликат дневного лога или сессии.
- **FR-011. Недельные цели.** Одновременно активно не более трёх целей.
- **FR-012. Сессия активности.** Добавление сессии требует одного основного действия; отмена доступна сразу после добавления.
- **FR-013. Нет данных.** Отсутствующий дневной лог не считается невыполнением.
- **FR-014. Итог дня.** Минимум выполнен, когда завершены все три обязательные опоры выбранного режима.
- **FR-015. История.** Основной экран не загружает полную историю; она доступна отдельным запросом.
- **FR-016. Недельный обзор.** Следующую неделю можно подготовить без копирования дат и дневных записей.
- **FR-017. Приватность MVP.** Приложение работает с единственным профилем владельца, не принимает произвольный `userId` от клиента и открывает персональные данные только после проверки серверной сессии.
- **FR-018. Экспорт.** Пользователь может выгрузить свои данные в машиночитаемом формате.
- **FR-019. Ошибки.** При ошибке сохранения введённые пользователем данные остаются в интерфейсе до повторной попытки.
- **FR-020. Неоднозначность.** Каждый интерактивный статус содержит текстовое описание результата действия.
- **FR-021. Защищённые маршруты.** Все страницы и API, кроме `/login`, login endpoint и `/api/health`, требуют действующую сессию.
- **FR-022. Единственный пользователь.** При первом запуске приложение создаёт или обновляет одного владельца из server-side конфигурации без публичной регистрации.
- **FR-023. Пароль.** Приложение хранит только Argon2id-хэш пароля; открытый пароль не сохраняется и не логируется.
- **FR-024. Сессия.** Успешный вход создаёт случайный непрозрачный токен, а в базе хранится только его хэш.
- **FR-025. Cookie.** Session cookie имеет атрибуты `HttpOnly`, `Secure`, `SameSite=Strict` и ограничение `Path=/`.
- **FR-026. Выход.** Logout удаляет текущую серверную сессию и cookie.
- **FR-027. Ограничение попыток.** Повторные неуспешные входы ограничиваются по IP и логину; сообщение не раскрывает наличие пользователя.
- **FR-028. Срок сессии.** Сессия имеет абсолютный срок действия, настраиваемый окружением; значение MVP по умолчанию — 30 дней.

## 11. API и сохранение данных

Конкретный транспорт определяется архитектурным решением, но интерфейс данных должен поддерживать:

- получение контекста сегодняшнего дня одним агрегированным запросом;
- создание или обновление дневного check-in;
- изменение выбранного режима;
- изменение статуса каждой опоры;
- получение текущей недели;
- добавление и отмену сессии недельной цели;
- сохранение недельного обзора;
- получение истории с пагинацией;
- настройку часового пояса и шаблонов опор;
- экспорт данных пользователя.

Мутации должны быть идемпотентными. Сервер получает владельца только из проверенной сессии и не принимает `userId` от клиента. При первом запуске единственный пользователь синхронизируется из доверенной server-side конфигурации. Все таблицы сохраняют поле владельца и репозитории данных требуют owner scope, чтобы позднее разрешить несколько аккаунтов без изменения доменной модели.

## 12. Состояния интерфейса

Каждый основной экран должен иметь состояния:

- загрузка без скачка макета;
- пустые данные с понятным следующим действием;
- сохранение;
- успешное сохранение;
- ошибка с возможностью повторить;
- отсутствие сети;
- недоступность backend;
- истёкшая или отозванная сессия;
- недоступный ресурс или 404.

Оптимистическое обновление допустимо для чекбоксов и добавления сессии, если при ошибке интерфейс возвращает предыдущее состояние и сообщает о проблеме.

## 13. Нефункциональные требования

### Адаптивность

- Основной сценарий работает без горизонтального скролла от 390 px.
- На ноутбуке главный экран не требует боковой панели для навигации.
- Интерактивные элементы имеют удобную область нажатия для сенсорного экрана.

### Доступность

- Все операции доступны с клавиатуры.
- Видимый фокус не отключается.
- Цвет и эмодзи не являются единственными признаками режима или статуса.
- Интерактивные элементы имеют доступные названия.
- Контраст соответствует WCAG 2.2 AA.
- Изменение статуса сохранения объявляется без перехвата фокуса.

### Производительность

- Первый экран не должен загружать полную историю.
- Целевой LCP на типичном мобильном соединении — не более 2,5 секунды.
- Отметка действия визуально подтверждается не позднее 100 мс после нажатия.
- Некритичные графики и история загружаются лениво.

### Надёжность

- Даты рассчитываются единообразно на клиенте и сервере.
- Граница дня и недели покрывается автоматическими тестами для нескольких часовых поясов.
- Повторная отправка мутации не создаёт дубликаты.
- Незавершённое сохранение явно видно пользователю.

### Безопасность и приватность

- Production-домен — только `https://habbit.merdev.site`; HTTP принудительно перенаправляется на HTTPS.
- Nginx Proxy Manager выполняет TLS termination, а приложение доверяет proxy-заголовкам только от собственного reverse proxy.
- Порт приложения доступен только reverse proxy или приватной Docker-сети; порт базы данных не публикуется наружу.
- Все персональные страницы и API требуют действующую серверную сессию.
- Логин, Argon2id-хэш пароля и параметры начального владельца передаются через server-side secrets; открытый пароль не хранится в репозитории или базе.
- Session token случайный, передаётся только в защищённой cookie; в базе хранится хэш токена.
- На login endpoint действует rate limit и одинаковый ответ для неверного логина и пароля.
- Клиент не передаёт и не выбирает идентификатор владельца; owner scope определяется сессией.
- Для изменяющих запросов проверяются допустимый HTTP method, Origin и действующая сессия.
- Заметки, HRV и оценки состояния не попадают в логи приложения и аналитику.
- Секреты не хранятся в клиентском bundle или репозитории.
- Секреты сессий и базы данных передаются через переменные окружения или secret storage хоста.
- Logout отзывает серверную сессию; смена пароля или session secret позволяет отозвать все существующие сессии.

## 14. Продуктовые метрики

### Основные

- `days_with_minimum_completed / days_with_check_in`.
- Медианное время утреннего check-in.
- Доля недель, для которых выполнен обзор.
- Выполнение недельных целей в формате `actual / target`.

### Диагностические

- Доля ручных изменений предложенного режима.
- Количество ошибок сохранения.
- Доля дней без записей отдельно от дней с частичным выполнением.

Содержимое личных заметок и значения HRV не отправляются в продуктовую аналитику.

## 15. Критерии приёмки MVP

1. При открытии приложения отображается локальная дата пользователя и корректная неделя.
2. Check-in из двух обязательных значений завершается менее чем за 30 секунд.
3. При энергии 1 или сне 1 предлагается `Минимум`.
4. При энергии 3 и сне не ниже 2 предлагается `Ресурс`.
5. Пользователь может изменить режим одним действием.
6. После check-in видно ровно три обязательные опоры.
7. Выполнение опоры сохраняется автоматически и переживает перезагрузку.
8. Повтор запроса не создаёт второй дневной лог или вторую сессию.
9. Спортивные активности увеличивают недельный счётчик движения вместо заполнения дневной матрицы.
10. Отсутствие дневного лога отображается как `нет данных` и не снижает показатель выполнения.
11. История не мешает основному сценарию и открывается отдельно.
12. Интерфейс работает без горизонтального скролла при ширине 390 px.
13. Основные действия доступны клавиатурой и имеют видимый фокус.
14. Приложение и база данных не доступны напрямую из публичной сети; клиент не может подменить owner scope.
15. Пользователь может завершить недельный обзор и подготовить следующую неделю без копирования дат.
16. Все девять формулировок опор соответствуют таблице режимов; каждый режим считается успешным только после выполнения своих трёх опор.
17. Актуальные опоры и цели можно внести вручную без импорта полной истории Notion.
18. Неавторизованный запрос к `/today` перенаправляется на `/login`, а API отвечает `401` без персональных данных.
19. Правильный логин и пароль создают cookie-сессию; неверные данные возвращают одинаковую общую ошибку.
20. В базе и логах отсутствуют открытый пароль и открытый session token.
21. После logout старая сессия не даёт доступа к защищённым маршрутам.
22. `http://habbit.merdev.site` перенаправляется на `https://habbit.merdev.site`.

## 16. Открытые архитектурные решения

Зафиксирован исходный технический вектор:

- Next.js и TypeScript;
- Node.js 24 LTS;
- pnpm 11;
- PostgreSQL и Prisma ORM;
- Tailwind CSS;
- self-hosted deployment в Docker на собственном сервере;
- Nginx как reverse proxy;
- один пользователь с логином/паролем и серверной cookie-сессией;
- Argon2id для хэширования пароля;
- отсутствие регистрации, восстановления пароля и ролей;
- отсутствие зависимости от Vercel-specific сервисов и runtime.

Инфраструктурные параметры задаются при развёртывании по `docs/deployment.md`:

- DNS-запись `habbit.merdev.site`;
- TLS-сертификат для `habbit.merdev.site`;
- доступ к панели `https://nginx.merdev.site`;
- расписание и внешнее хранилище резервных копий PostgreSQL.

Открытыми после MVP остаются:

- необходимость PWA и офлайн-режима после MVP;
- способ экспорта данных;
- формат продуктовой аналитики без передачи чувствительных значений.
